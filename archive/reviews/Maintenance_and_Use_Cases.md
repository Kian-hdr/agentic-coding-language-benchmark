# Maintenance, platform fit, and lifetime cost

Research refreshed 26 October 2026. Companion to `Evaluation_Report.md`; this document adds documentation-backed interpretation, not new performance measurements. Eligibility tiers below are judgments for this adoption decision, not vendor certifications or survival probabilities.

No inspected source established a binding multi-year support agreement or financial runway for the three specialized languages. Foundation membership and current commits are useful signals, not guarantees. Fully available permissively licensed source improves the fallback path, but maintaining a compiler still requires expertise and funding.

## Runtime efficiency depends on the implementation path

**Python loops and scientific Python are different comparisons.** NumPy documents homogeneous arrays and operations executed in compiled code, including vectorization and broadcasting. A standard-library-only Python implementation excludes that path. Therefore a loop-heavy CLI result cannot establish the cost of a production NumPy pipeline. Separately test conversion/copy overhead, batching, array dtype, temporary allocations, BLAS thread settings and complete end-to-end work. Native kernels do not accelerate every branching algorithm, and small inputs can be dominated by setup. [NumPy explanation](https://numpy.org/doc/stable/user/whatisnumpy.html)

**Rust is a strong CPU/memory-control candidate, not a promised speed winner.** Its ownership checks happen during compilation rather than through tracing garbage collection. Allocation patterns, cloning, algorithm selection, debug versus release compilation, and dependencies can dominate measured outcomes. Safe Rust's checks do not prove business correctness, and unsafe/FFI boundaries need separate scrutiny. [Ownership model](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)

**Go offers a useful services tradeoff.** Its garbage-collector guide explicitly explains the CPU/memory tradeoff: reducing collection frequency can save CPU at the cost of more memory. Evaluate live heap, allocation rate, RSS, concurrency, GC work and tail latency together. A small one-process ledger does not establish performance of a long-running server. [GC guide](https://go.dev/doc/gc-guide)

**TypeScript runs through a JavaScript runtime.** Node worker threads can run CPU-intensive JavaScript in parallel; they are not an automatic improvement for ordinary asynchronous I/O. Worker startup and data transfer introduce costs. A benchmark must distinguish single-thread event-loop execution from an explicitly parallel implementation. [Node documentation](https://nodejs.org/api/worker_threads.html)

## Platform fit can outweigh a CLI score

Apple's SwiftUI provides a native interface framework across Apple platforms; Android documentation recommends Jetpack Compose for native Kotlin UI. Browser applications need browser APIs, accessibility, rendering and framework integration. None of these capabilities is represented by JSON account arithmetic. [SwiftUI](https://developer.apple.com/swiftui/), [Kotlin Android](https://kotlinlang.org/docs/android-overview.html)

A responsible follow-up compares the actual application path: UI responsiveness, accessibility, startup, background behavior, platform permissions, device memory/energy and packaging/release workflows. Language portability, UI-framework portability and library availability are distinct. Kotlin multiplatform and Swift Android support deserve target-specific qualification rather than dismissal, but their existence does not make a CLI test an app benchmark.

## Break-even and lifetime cost

Use a measured cost model, not one overall language score:

`lifetime cost = migration + development + validation + operation + maintenance + expected incidents + exit cost`

A migration breaks even only when conservative recurring savings over the intended lifetime exceed migration, retraining, compatibility, rollout and fallback costs. Compute an interval with low/high traffic and staffing assumptions; do not manufacture precise dollar savings from CPU milliseconds. CPU time, RSS and wall time are different quantities; reserved cloud memory or idle capacity may dominate billing. Correctness and platform eligibility are gates before speed enters the decision.

Prefer incremental hot-path replacement over a rewrite when it isolates measurable benefit. Keep external schemas, contract tests, deployment recipes, pinned recoverable toolchains and a fallback path. Charge interop serialization, copying and operational complexity to the proposed replacement. Reassess the benefit after ordinary optimization in the existing language.

The earlier two-trial authoring pilot supports choosing candidates for this next stage. It cannot estimate rare defect rates, long-term maintenance effort, model-version robustness or likelihood of vendor survival. A faster incorrect result receives no production credit. More reliable evidence comes from independent tasks, repeated maintenance changes, held-out edge cases, target-device tests and observation over supported upgrades.

A public app must pass the intersection of language target, framework, dependencies, CPU instruction set, OS version and distribution channel. A compiler that emits an executable is not an installer, signed application, store acceptance or usable UI.

### FFI, upgrade and binary compatibility

Source compatibility does not guarantee binary compatibility. CPython extensions normally need the matching minor-version ABI unless they deliberately use a Stable ABI; verify wheel tags and free-threaded variants. Swift has stable ABI on Apple platforms, but independently distributed binary frameworks need module/library-evolution settings. Rust's default type layout can change between compilations; use deliberate C ABI/layout interfaces or rebuild linked components rather than assume a stable Rust shared-library interface. Go's Go1 contract is source-level; rebuild packages across toolchain releases. [Python ABI](https://docs.python.org/3/c-api/stable.html), [Swift evolution](https://www.swift.org/blog/library-evolution/), [Rust layout](https://doc.rust-lang.org/reference/type-layout.html), [Go contract](https://go.dev/doc/go1compat)

FFI adds ownership, encoding, exceptions/error mapping, threading, cancellation and library-loader compatibility concerns. A portable process/schema boundary can reduce ABI coupling while adding startup and serialization costs. Test both sides of upgrades, including rollback, not just recompilation.

### Additional research candidates, outside these nine benchmark results

- **C#/.NET:** strong candidate for .NET services, Windows software and Unity games. MAUI supports Android/iOS/macOS through Catalyst/Windows; its official matrix does not include Linux desktop. Linux UI needs a separately chosen framework. Runtime-dependent, self-contained and AOT choices have different packages/limits. Do not conflate .NET, MAUI and Unity platform matrices. [MAUI](https://learn.microsoft.com/en-us/dotnet/maui/supported-platforms), [Unity requirements](https://docs.unity3d.com/6000.0/Documentation/Manual/system-requirements.html)
- **Java:** established JVM/server and desktop option. `jpackage` builds platform installers with an application runtime, so users need not manage a separate JDK; packaging must run on the target OS. JVM compatibility does not make modern Java desktop UI an iOS UI solution. [Oracle packaging](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html)
- **C++:** important for game engines, existing native SDKs and Qt applications. Qt supports multiple desktop/mobile/WebAssembly configurations, but platform versions, toolchains, CPU support and licensing are version-specific. C++ ABI and native dependencies require deliberate compiler/runtime coordination. [Qt matrix](https://doc.qt.io/qt-6/supported-platforms.html)
- **Mojo:** investigate for CPU/GPU kernels and Python/C integration, rather than broad consumer app UI. Current official docs show 1.2.0 and newly open source; do not reuse an old closed-source label. Documented environment requires macOS15+ Apple Silicon, or Linux glibc2.34+ on x86-64-v3/ARM64 NeoverseN1+; Windows is WSL-only. Compiler target lists do not establish shipping support for every target, mobile UI or native Windows. Shared-library use can require Modular runtime libraries. [requirements](https://mojolang.org/docs/requirements/), [compilation/runtime](https://mojolang.org/docs/tools/compilation/)

A release-qualified compatibility result needs a real artifact installed on a clean target device/VM for each promised OS/CPU/version combination, no developer runtime assumptions, working UI/accessibility/features, signed packages where required, safe updates and rollback. Those tests remain outstanding. No public deployment or additional language benchmark is implied by this research.
